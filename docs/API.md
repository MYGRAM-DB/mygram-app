# معيار واجهات API

## 1. الحالة

لا توجد حالياً واجهات API خاصة بالتطبيق موثقة على `main`. تُنشأ هذه الوثيقة كمعيار قبل إضافة أي endpoint أو Edge Function جديدة.

## 2. توزيع المسؤوليات

- عمليات القراءة والكتابة الاعتيادية للمستخدم يمكن أن تستخدم Supabase Data API عندما تكون السياسة واضحة ومختبرة.
- العمليات التي تحتاج أسراراً أو تحققاً معقداً أو قفل معاملات أو تكاملاً خارجياً يجب أن تمر عبر Edge Function أو خادم موثوق.
- لا يجوز للعميل تنفيذ قرار إداري أو مالي بمجرد إخفاء زر في الواجهة.
- لا يُستخدم Service Role Key إلا على الخادم وفي أقل نطاق ممكن.

## 3. تسمية الخدمات

كل منتج يملك نطاق API مستقلاً، مع الخدمات المشتركة في طبقة واضحة. أمثلة أسماء وظيفية مقترحة وليست endpoints منشورة بعد:
- `identity/profile`
- `social/posts`
- `messenger/conversations`
- `whatsmygram/conversations`
- `media/sign-upload`
- `meetings/create-token`
- `wallet/transfer` (محجوز للمستقبل وغير منفذ)

لا تُعلن هذه الأمثلة كواجهات متاحة قبل وجود تنفيذ واختبار.

## 4. عقد الطلب والاستجابة

كل خدمة جديدة توثق:
- الاسم والمسار وطريقة HTTP.
- المصادقة والتحقق من هوية المستخدم.
- المورد الذي يجري الوصول إليه.
- الصلاحيات المطلوبة.
- المدخلات والتحقق منها.
- المخرجات وأنواعها.
- الأخطاء المعروفة وكيفية التعامل معها.
- حدود الاستخدام والمهلة.
- اختبارات السماح والمنع.

عقد Edge Function المقترح:
- نجاح: جسم JSON محدد النوع مع معرف المورد أو نتيجة العملية.
- فشل: رمز خطأ ثابت ورسالة آمنة لا تكشف تفاصيل قاعدة البيانات أو الأسرار.
- يضاف `request_id` للتتبع عندما تتوفر طبقة تسجيل موحدة.

## 5. التزامن والتكرار

- تستخدم `Idempotency-Key` للعمليات التي قد يعيد العميل إرسالها.
- تُنفذ التحويلات أو العمليات متعددة السجلات داخل معاملة ذرية.
- لا يُعتمد الرصيد أو الحالة على قيمة يرسلها المتصفح.
- لا يُستخدم polling سريع كبديل دائم عن Realtime عندما تكون الاشتراكات مصممة ومختبرة.

## 6. إصدار وتوثيق

- توثق كل واجهة في هذا الملف أو في ملف مجالها.
- تُحدّث TypeScript database types بعد تغييرات المخطط.
- يجب أن تكون أسماء الحقول متطابقة بين DB والعميل والعقد.
- لا تنشأ واجهتان للغرض نفسه بلا سبب تقني موثق.
