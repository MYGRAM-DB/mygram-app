## 4. فحص RLS الذي نُفذ على Staging

في معاملة اختبار واحدة بدور PostgreSQL authenticated تم تعيين claim لهويتين مختلفتين من حسابات Staging الحالية. لم تُستخدم كلمات مرور أو رموز جلسات حقيقية.

النتائج:
- profiles: المالك تمكن من update؛ المستخدم الآخر لم يتمكن من update، لكنه استطاع قراءة الملف كما تسمح السياسة الحالية.
- posts/comments/reactions: المالك تمكن من الإنشاء؛ المستخدم الآخر استطاع القراءة، ولم يستطع update/delete أو الإدراج باسم المالك.
- post_comments: تم اختبار إدراج تعليق ورد متداخل.
- user_preferences: لم تظهر تفضيلات المالك للحساب الآخر؛ فشلت محاولات update والإدراج باسمه.
- الاختبار كله داخل BEGIN ... ROLLBACK؛ والتحقق اللاحق أكد أن صفوف posts/comments/reactions/preferences بقيت صفراً.

**حدود النتيجة:** هذا اختبار فعلي لسياسات PostgreSQL مع role وclaim محاكيين، لكنه ليس جلستي Auth مستقلتين باستخدام JWT عبر Supabase REST. تبقى رحلة API الحقيقية بحسابين منفصلين بوابة مطلوبة.

## 5. جدول التفاصيل الخاصة والدول

- تم التحقق من أن RLS مفعّل على profile_private_details وsupported_countries.
- تم فحص سياسات المالك فقط للتفاصيل الخاصة وصلاحيات الأعمدة. authenticated يستطيع تعديل contact_email/phone، ولا يملك UPDATE على verified_contact_method أو contact_verified_at.
- anon لا يملك SELECT على profile_private_details، ولا يملك كتابة حقول إثبات التحقق.
- جدول الدول لديه 205 سجلات مفعلة؛ صلاحية القراءة لـanon/authenticated، ولا صلاحية INSERT لـanon.
- لم يتم تنفيذ كتابة runtime لصفوف التفاصيل الخاصة في هذا الفحص؛ لذلك تبقى اختبارات API بحسابين مطلوبة لجدول التفاصيل الخاصة.

## 6. ما لم يُختبر بعد

- Auth حي: signUp، تأكيد البريد، signIn، استرجاع كلمة المرور.
- E2E مسار onboarding بعد جلسة Auth حقيقية، وحفظ النموذج من المتصفح عبر Supabase REST/RPC.
- اقتراح اسم مستخدم وفحص توفره المبكر.
- اختبار RLS عبر JWT حقيقيين منفصلين، لا محاكاة قاعدة البيانات فقط.
- اختبار complete_mygram_profile بحسابين JWT حقيقيين عبر REST، والتحقق من أن حقول الملف الخاص والتفضيلات لا تُقرأ من الحساب الآخر.
- اختبار منع المستخدم من تعديل verified_contact_method أو contact_verified_at عبر REST.
- اختبار API حي لعدم القدرة على تمرير هوية مستخدم آخر إلى RPC.
- إرسال بريد أو SMS حقيقي.
- مكالمات WebRTC/LiveKit على جهازين.
- الميزات الاجتماعية والمراسلة بعد بناء الواجهات الجديدة.
- Storage بحسابين منفصلين.

## 7. مصفوفة القبول

- التسجيل بالبريد وتأكيده واستعادة كلمة المرور.
- استكمال الملف والتحقق من username وتعارض case-insensitive.
- حفظ DOB والجنس والاتصال في الجدول الخاص، ومنع قراءة مستخدم آخر.
- إنشاء منشور وتعليق ورد وتفاعل وخصوصية المحتوى.
- القصص والريلز والصداقة والمجتمعات.
- Messenger الفردي والجماعي والوسائط.
- WHATSMYGRAM المستقل وحساب الهاتف.
- Meeting: إنشاء وانضمام ومضيف ومشارك ومكالمة فعلية.
- تبديل اللغة والاتجاه.
- اختبار اثنين أو أكثر من الحسابات في جلسات متصفح مستقلة.

## 8. بيئات الاختبار

- Staging هو هدف اختبارات التكامل الحساسة.
- لا تستخدم بيانات مستخدمين حقيقيين في الاختبارات الاصطناعية.
- تحفظ الأسرار في إعدادات البيئة ولا تضاف للمستودع.
- لا تستخدم Service Role Key في المتصفح.
- بعد النشر ينفذ Smoke test دون كتابة بيانات اختبار إلى حسابات حقيقية.
