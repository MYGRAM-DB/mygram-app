# سجل القرارات الفنية

## قرارات معتمدة

| القرار | التوجيه |
|---|---|
| مستودع البناء | `MYGRAM-DB/mygram-app` |
| الفرع الأساسي | `main` |
| نقطة الانطلاق | مراجعة ما قبل التفريغ ثم إعادة تنظيم وبناء جديد على أساس main |
| البيئات | Production نهائية، وStaging مستقلة للتحقق قبل التغييرات الحساسة |
| حماية البيانات | لا حذف بيانات مستخدمين، ولا تعطيل RLS، ولا Migration مدمرة |
| الهوية | Supabase Auth معرف موحد، والملف العام عبر `profiles` بعد تدقيق التوافق القديم |
| حدود المنتجات | تسعة منتجات مستقلة، مع خدمات مشتركة مضبوطة |
| WHATSMYGRAM | يبقى مستقلاً عن MYGRAM MESSENGER |
| النشر | لا نشر Production قبل بوابات Staging والاختبار |
| المحفظة | لا عمليات مالية حقيقية قبل مواصفات التوزيع والدفتر والامتثال |

## قرارات هندسية تنفيذية

- تُحفظ جداول الدردشة الخاصة بـWHATSMYGRAM مستقلة.
- يُعامل MYGRAM Chat التاريخي كمكوّن ضمن MESSENGER، لا منتج عاشر، مع توثيق أي اختلاف لاحق.
- لا يُنقل كل مخطط Production من `public` إلى schemas جديدة في مرحلة التأسيس؛ هذا قد يكسر Data API والواجهات الحالية. تُراجع خيارات العزل بعد استقرار العقود.
- لا تُحذف جداول `users` و`messages` التاريخية حتى يكتمل جرد المراجع وخطة ترحيل قابلة للاستعادة.

## مسائل غير محسومة

1. توزيع 15B/15B/20B على MYGRAM COIN وDinGram وDirGram.
2. أساس حساب 10% حرق و90% خزينة وتوقيت تطبيقها.
3. سياسة أهلية ومنح 10,000 لأول 5 ملايين مستخدم، والعملة والوحدة.
4. مزود SMS الأفضل حسب البلدان المستهدفة والكلفة الحقيقية.
5. مزود SMTP النهائي وحجم الاستخدام وتوثيق نطاق الإرسال.
6. هل تبقى GitHub Pages هي استضافة واجهة SPA النهائية أم تُعتمد استضافة أخرى بعد مقارنة متطلبات المنتج.
7. حدود الخصوصية والجمهور الافتراضية للمنشورات والملفات والملفات الشخصية.

لا تُحوّل هذه المسائل إلى قيم تشغيلية بمجرد افتراضات برمجية.
