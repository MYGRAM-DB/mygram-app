# خطة التراجع والاستعادة

## 1. قاعدة عامة

التراجع عن كود الواجهة أسهل من التراجع عن تغيير مخطط قاعدة البيانات. لذلك يجب تصميم Migration لتكون متوافقة مع الإصدار السابق قدر الإمكان.

## 2. التراجع عن الكود

- يسجل كل إصدار Commit SHA وPR ورابط النشر.
- عند عطل في الواجهة يمكن إعادة النشر من آخر Commit معروف سليم.
- لا تستخدم Force Push على `main`.
- لا تحذف فروع أو tags مرتبطة بإصدار مطلوب للاستعادة قبل التحقق منها.

## 3. التراجع عن قاعدة البيانات

- الأفضل إصلاح Migration جديدة للأمام بدلاً من إسقاط عمود أو جدول مستخدم.
- يجب أن تكون التغييرات additive عند الإمكان.
- لا يُنفّذ DROP/TRUNCATE أو إسقاط قيود أو حذف صفوف مستخدمين كوسيلة تراجع روتينية.
- قبل تغيير بيانات، وثق عدد الصفوف المتأثرة وطريقة الاستعادة.
- يجب التحقق من توافر النسخ الاحتياطية الفعلية وقيود الخطة؛ لا يُفترض وجود Point-in-Time Recovery على خطة لا توفره.

## 4. بوابة ما قبل Migration

- فحص الجداول والقيود والسياسات والـTriggers الحالية.
- اختبار Migration على Staging.
- التحقق من البيانات بعد التطبيق.
- إعداد معالجة فشل أو Migration تصحيحية.
- عدم اعتماد نجاة Workflow وحدها.

## 5. بيانات لا تُحذف في إعادة البناء

- Auth users.
- Profiles والملفات الشخصية الخاصة.
- Posts/comments/reactions.
- رسائل ومرفقات المستخدمين.
- بيانات الاجتماعات والمحاضر.
- سجلات مالية مستقبلية ودفاتر القيود.

لا يُحذف أي مورد من هذه الموارد إلا وفق سياسة منتج وقانون واضحة، وبعد موافقة مسار الحذف المعتمد.
